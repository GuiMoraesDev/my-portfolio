**Engineering principles**

## English

**How I think about product and engineering decisions.**

Not just values I claim to have. These are insights I've come to after building projects at very different stages. Some I got right the first time, but most came with experience.

### 01. How I think: The code is not the product. The solution is.

Messy code is not always a sign of bad decisions. Sometimes it was the right call at the time. Refactoring comes when you start working as people, not because the code is aesthetically displeasing, but when the gain is real.

### 02. How I decide: Start it simple or write down why.

The code outlasts the reasoning behind it. Without context, all that's left is speculation for those who come after. Documented tradeoffs are the only thing that closes that gap.

### 03. How I start: Direction before momentum.

The first question is never which framework or stack to use. It's what the user actually needs to solve. With that clear, the architecture follows. Without that, you'll just arrive at the wrong place sooner.

### 04. How I ship: Optimize for the next person, not the next deploy.

Fast delivery and clean systems aren't opposites. Naming, structure, and interfaces compound over time, for better or worse. Team speed is to write for the person who comes next.

### 05. How I collaborate: To work as a team, not as an individual contributor.

Unblocking someone beats shipping alone. Well-scoped PRs, readable code, clear decisions. None of it goes on a roadmap, but it's what keeps a team actually moving.

## Português

**Como penso sobre decisões de produto e engenharia.**

Não são só valores que eu declaro ter. São entendimentos que fui chegando depois de construir projetos em estágios bem diferentes. Algumas acertei de primeira, mas a maioria veio com a experiência.

### 01. Como eu penso: O código não é o produto. A solução é.

Código bagunçado nem sempre é sinal de decisão errada. Às vezes era a escolha certa naquele momento. A refatoração vem quando começa a travar as pessoas, não porque o código incomoda esteticamente, mas quando o ganho é concreto.

### 02. Como eu decido: Comece simples ou anota o porquê.

O código deve sobreviver ao raciocínio por trás dele. Sem contexto, so sobra suposições pra quem vem depois. Tradeoffs documentados são a única coisa que fecha essa brecha.

### 03. Como eu começo: Direção antes de momentum.

A primeira pergunta nunca é qual framework ou stack usar. É o que o usuário precisa realmente resolver. Com isso claro, a arquitetura segue. Sem isso, você só vai chegar mais cedo no lugar errado.

### 04. Como eu entrego: Otimize para a próxima pessoa, não para a próxima implementação.

Entrega rápida e sistemas limpos não são opostos. Nomenclatura, estrutura e interfaces se acumulam com o tempo, pra melhor ou pior. Velocidade de time é escrever pensando em quem vem depois.

### 05. Como eu colaboro: Trabalhar em equipe, não individualmente.

Desbloquear alguém é melhor que entregar algo sozinho. PRs bem escopados, código legível, decisões claras. Nada disso entra no roadmap, mas é o que mantém o time andando de verdade.
